# TicketFlow ERP 运维提单系统 V1.0 实施设计

日期：2026-10-21。按用户授权重新设计标准版 P0+P1；本文件为本次实施基线，不冒充原聊天不可读取的方案正文。生产部署仍需用户单独确认。

## 目标与边界
面向单企业 ERP 使用人员、运维处理人及管理员，完成问题提交、分派、协作、解决确认及追踪。V1 不包含多租户、ERP 数据写回、自动执行运维命令、复杂审批流设计器或收费系统。

## 角色与数据权限
申请人可提交和查看本人及明确参与的工单，补充说明、附件、确认解决或申请重开。处理人可查看所在处理组工单、接受分派、处理及解决；跨组访问由管理员授予。管理员维护账号、部门、处理组、分类、优先级、SLA 和指派规则，查看全量数据与审计。内部备注仅处理人及管理员可见。所有接口在后端校验对象权限，前端隐藏按钮仅用于交互。
当前基础版处理人可查看所有工单，需在正式验收前收敛到处理组权限。

## P0 必备功能
- 账号：管理员创建用户、启停账号、修改密码、角色及处理组管理；无公开注册。Argon2 密码摘要，登录限流，JWT 过期及撤销策略，生产 HTTPS。
- 工单：编号、标题、描述、ERP/运维类型、系统模块、影响范围、优先级、申请人、处理组、处理人、状态、创建/更新时间。标题 1–200 字，正文不超过 20000 字。
- 流程：待受理→处理中→待确认→已关闭；待确认可退回处理中；已关闭重开需填写理由并记录审计。管理员可取消并记录理由；普通处理人不得跳过流程。
- 分派：管理员指定处理组及处理人；处理人仅能操作授权范围，转派需理由并留下记录。
- 协作：公开评论、内部备注、附件；附件仅经鉴权接口下载，随机存储名，限制类型与大小，不执行上传内容。
- 查询：编号、关键词、状态、分类、优先级、申请人、处理人、日期筛选；服务端分页，每页上限100。
- 审计：创建、字段变更、转派、状态变化、评论、附件操作均记录操作者和 UTC 时间；普通用户不得删除审计记录。
- 运维基础：数据库迁移、健康与就绪探针、结构化日志、敏感值脱敏、备份恢复说明与 CI。

## P1 标准版功能
- SLA：工作日/工作时段及节假日配置；按优先级计算首次响应和解决期限，待申请人补充时可暂停解决计时；重开规则保留原周期并建立新周期。定时任务以数据库唯一键保证提醒幂等。
- 通知：站内通知必备，邮件作为可配置渠道；创建、分派、评论、解决及超时触发。后台重试，发送失败可见，不阻塞提交工单。外部邮件服务配置后才启用。
- 看板：待处理、处理中、超时数、响应及解决时长；按组/分类/日期统计。权限与工单列表一致。
- 知识库：从已解决工单整理文章，草稿/发布；搜索、分类、关联工单，发布由管理员或授权处理人执行。
- 导出：按当前权限及筛选条件导出 CSV，防公式注入，限制行数；下载与导出记录审计。

## 架构与数据
前端 Vue 3 + TypeScript + Vite + Element Plus；后端 FastAPI + SQLAlchemy + Alembic；PostgreSQL 16。小规模首版使用独立 worker 轮询数据库任务表，无需在 2GiB 主机上额外引入 Redis。附件存独立持久卷，生产可迁移 OSS；默认不公开桶。
核心表：users、departments、teams、team_members、tickets、ticket_participants、comments、attachments、ticket_events、sla_policies、sla_cycles、notifications、outbox_jobs、knowledge_articles、audit_logs。所有业务时间存 UTC，界面以 Asia/Shanghai 显示。工单使用 version 乐观锁避免并发覆盖；工单变化、审计和通知任务同事务提交。
接口统一位于 /api；错误含稳定代码及请求编号；列表返回 items/total/offset/limit；API 文档仅在授权范围开放。附件流式读取；所有文本默认按纯文本渲染。

## 交互
中文桌面及移动端工作台：我的工单、处理队列、工单详情、知识库、通知、管理。详情显示状态轨迹、影响范围、处理人和完整时间线。表单有必填验证、提交中禁用、失败保留输入。优先级及状态使用中文标签，不仅依赖颜色。指派使用可搜索用户选择器，不要求输入用户编号。

## 实施顺序及验收
1. M1：基础闭环、权限、迁移及自动测试。现有代码为此阶段起点；补齐权限组、审计时间、并发控制、限流和管理界面。
2. M2：附件、SLA、通知、看板、知识库、导出，逐项提交并配套验收。
3. M3：ECS 只读盘点，确定隔离路径/端口/域名、备份恢复、资源预算和回滚方案；用户批准后才生产部署。
验收覆盖角色与跨对象越权、合法/非法流转、并发冲突、附件鉴权、SLA工作时间及暂停、通知幂等、导出权限与注入防护；真实PostgreSQL迁移与恢复演练；浏览器完成提交—分派—评论—解决—确认全流程。未完成项必须保持开放，不以脚手架代替验收。

## ECS 与部署约束
已从控制台读取：上海实例 ele，Ubuntu24.04，2vCPU/2GiB，公网带宽3Mbps。具体地址及安全组信息存本地环境检查报告，避免写入常规公开文档。CPU/内存监控为控制台瞬时值，不能替代主机资源盘点。
生产使用构建后的静态前端、独立 API/worker/PostgreSQL 容器及独立卷；只绑定回环地址，通过现有代理新增独立域名入口，须先查清80/443归属。禁止覆盖既有Compose、代理配置、卷或服务。目标运行内存须实测；若剩余资源不足则提出扩容或独立主机方案，不自动购买或调整实例。
发布前备份数据库与附件并验证恢复；迁移先在副本演练。回滚以兼容旧版数据结构为前提，不对已有生产数据盲目执行 downgrade。
